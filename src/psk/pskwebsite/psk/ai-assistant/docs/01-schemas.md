# Schema Design

> **All data in this repository is MOCK/EXAMPLE data** for building and testing an
> assistant. Legal and business policy fields are deliberately left as placeholders —
> they must be replaced with your company's actual published documentation before
> anything ships.

---

## 0. The core architectural split

The single most important decision in this design:

| Concern | Source of truth | Storage | Retrieval |
|---|---|---|---|
| **Where things live** (routes, IDs, availability) | Deterministic entity registry | PostgreSQL | Exact lookup / trigram / BM25 |
| **What things mean** (rules, FAQs, policies) | Knowledge documents | Vector DB + Postgres | Hybrid (BM25 + vector) |
| **Live user state** (balance, bets, KYC status) | Application API | Never stored in RAG | Tool call at request time |

**The vector database never decides where to navigate.** It can *suggest* an entity,
but the route is always resolved from the registry by `entity_id`. This is what stops
the model inventing `/games/aviator-pro-max` that returns a 404.

```
user query
    │
    ├─→ intent classifier ──→ NAVIGATE ──→ entity resolver (Postgres) ──→ route lookup ──→ action
    │                                            │
    │                                            └─→ low confidence ──→ clarification
    │
    ├─→ FAQ / GAME_INFO / POLICY ──→ hybrid retrieval ──→ grounded answer + citations
    │
    └─→ ACCOUNT / BALANCE / BET_STATUS ──→ API tool call ──→ never from RAG
```

## 1. Navigation entity schema

The deterministic registry. **Not embedded as prose** — see §12 for the nuance.

```jsonc
{
  "id": "game_aviator",           // canonical, stable, never reused
  "type": "GAME",                 // GAME | CATEGORY | SPORT | PAGE | ACCOUNT | POLICY | SUPPORT
  "name": "Aviator",              // display name
  "aliases": ["plane game", ...], // what users actually call it
  "description": "...",           // one line, used for disambiguation prompts
  "category": "Crash Games",
  "parent_id": "category_crash_games",
  "route": "/games/aviator",      // resolved by backend, never generated by the LLM
  "keywords": ["crash", "plane"],
  "status": "active"              // active | inactive | maintenance | geo_restricted
}
```

**Field notes**

- `id` — the contract between the model and your backend. The model outputs this; the
  backend maps it to a route. Changing an `id` breaks trained examples, so treat it as
  permanent.
- `aliases` — the workhorse for recall. Must include misspellings, slang, and
  transliterated forms. Populated from `aliases.json` at ingestion.
- `status` — the assistant must check this. Navigating a user to a disabled game is a
  worse failure than saying "that isn't available right now".
- `route` — present in the registry, but the model is never shown it in a way that
  lets it improvise. It emits `entity_id`; the backend does the lookup.

## 2. Page schema

Distinct from entities because a page describes *what can be done there*, which drives
the action buttons in the UI.

```jsonc
{
  "page_id": "page_deposit",
  "page_name": "Deposit",
  "page_type": "TRANSACTIONAL",   // LANDING | LISTING | DETAIL | TRANSACTIONAL | ACCOUNT | INFORMATIONAL | SUPPORT
  "route": "/wallet/deposit",
  "parent_page": "page_wallet",
  "description": "...",
  "keywords": [],
  "aliases": [],
  "available_actions": ["OPEN_DEPOSIT", "OPEN_WALLET"],
  "requires_auth": true,
  "requires_kyc": false
}
```

`requires_auth` / `requires_kyc` let the assistant pre-empt a dead end: sending a
logged-out user to `/wallet/withdraw` produces a login wall, not a withdrawal.

---

## 3. Game knowledge schema

RAG content. Informational only.

```jsonc
{
  "game_id": "game_aviator",      // MUST match the navigation entity id
  "name": "Aviator",
  "category": "Crash Games",
  "description": "...",
  "how_to_play": "...",
  "basic_rules": "...",
  "terminology": [{ "term": "Cash Out", "definition": "..." }],
  "common_questions": [{ "q": "...", "a": "..." }],
  "responsible_gaming_note": "...",
  "route": "/games/aviator",
  "content_status": "EXAMPLE_DATA"  // flags this as mock, not verified product copy
}
```

**Hard constraint:** no field may contain expected value, RTP claims, win probability,
"best strategy", or any suggestion that an outcome can be predicted. Crash and slot
outcomes are RNG-determined and independent. The `responsible_gaming_note` is
mandatory on every record, not optional.

## 4. FAQ schema

```jsonc
{
  "id": "faq_deposit_003",
  "question": "Why is my deposit still pending?",
  "answer": "...",                    // 2–4 sentences, self-contained
  "category": "DEPOSIT",
  "keywords": [],
  "related_pages": ["page_deposit"],  // drives action buttons under the answer
  "source_type": "FAQ",
  "priority": "high",                 // high | medium | low — a retrieval tiebreaker
  "requires_verified_source": false   // true where the answer depends on your policy
}
```

`requires_verified_source: true` means **the answer is a structural placeholder, not a
fact**. The assistant must either refuse to state specifics or route the user to
support. This is how we avoid inventing processing times and limits.

## 5. Policy schema

```jsonc
{
  "id": "policy_withdrawal_001",
  "title": "Withdrawal Policy",
  "content": "[REPLACE WITH ACTUAL COMPANY POLICY]",
  "category": "WITHDRAWAL_POLICY",
  "requires_verified_source": true,
  "jurisdiction": "[REPLACE — policy varies by licence]",
  "last_reviewed": null,
  "owner": "legal"
}
```

Policy records ship as placeholders **by design**. A plausible-sounding invented
withdrawal policy is a regulatory and consumer-harm problem, not a content gap.

## 6. Intent schema

```jsonc
{
  "query": "take me to aviator",
  "intent": "NAVIGATE",
  "entity": "Aviator",
  "entity_id": "game_aviator",
  "entity_type": "GAME",
  "expected_action": "OPEN_GAME",
  "confidence": 0.98,
  "requires_confirmation": false,
  "language": "en"                 // en | hinglish | hi_latin | te_latin | mixed
}
```

### Intent taxonomy

| Intent | Resolves via | Navigates? |
|---|---|---|
| `NAVIGATE` | Entity registry | Yes |
| `SEARCH` | Registry + BM25 | Shows list |
| `GAME_INFO` | Vector (game knowledge) | No, offers action |
| `FAQ` | Hybrid | No, offers action |
| `DEPOSIT` / `WITHDRAW` | Registry | Yes (auth-gated) |
| `BET_HISTORY` / `ACCOUNT` / `KYC` | Registry + API | Yes (auth-gated) |
| `PROMOTION` | Hybrid | Optional |
| `SUPPORT` | Registry | Yes |
| `RESPONSIBLE_GAMING` | Curated — always answer | Yes |
| `AMBIGUOUS` | Clarification | No |
| `UNKNOWN` | Fallback | No |

## 7. Confidence policy

Thresholds are the safety valve. Recommended starting points, to be tuned on your
own eval set:

| Confidence | Behaviour |
|---|---|
| `≥ 0.90` | Navigate directly |
| `0.70 – 0.89` | Navigate, but show "did you mean X?" alongside |
| `0.45 – 0.69` | **Ask for clarification**, offer top 2–3 candidates |
| `< 0.45` | Fall back to search results or support |

Two rules that override the table:

1. **Never auto-navigate a financial action** (`DEPOSIT`, `WITHDRAW`) below `0.95`.
   Confirm first.
2. **Never auto-navigate to an `inactive` entity** at any confidence.

## 8. Conversation state schema

Follow-ups ("take me there") need a resolvable referent.

```jsonc
{
  "session_id": "...",
  "turns": [...],
  "focus_stack": [                 // most recent first, capped at ~5
    { "entity_id": "game_aviator", "entity_type": "GAME", "mentioned_at_turn": 3 }
  ],
  "last_action": "NONE",
  "pending_clarification": null
}
```

A pronoun ("it", "there", "that one") resolves against `focus_stack[0]`. If the stack
is empty or the last two turns changed subject, the correct behaviour is to **ask**,
not to guess.

## 9. Action schema

```jsonc
{
  "action": "OPEN_GAME",
  "requires_entity_type": "GAME",
  "requires_auth": false,
  "requires_kyc": false,
  "confirm_before_execute": false,
  "route_source": "entity_registry"   // never "llm_generated"
}
```

`route_source` is enforced in code: the action executor accepts an `entity_id` and
looks the route up. It has no code path that accepts a URL string from the model.

## 12. What gets embedded — and what must not

| Dataset | Embed? | Why |
|---|---|---|
| FAQ answers | **Yes** | Natural-language questions need semantic match |
| Game knowledge | **Yes** | "how does the plane game work" ≠ lexical match |
| Help articles | **Yes** | Long-form, paraphrased queries |
| Policies | **Yes**, once real | Placeholders should be embedded but flagged |
| Entity aliases | **Partly** — see below | |
| Routes | **Never** | A route is a lookup, not a meaning |
| Page registry | **No** | Exact/BM25 lookup is faster and exact |
| Balances, bets, KYC status | **Never** | Live, per-user, and stale the moment it's stored |

**The alias nuance:** embed a short synthetic sentence per entity
("Aviator is a crash game, also called the plane game") to catch semantic
near-misses. But the vector hit returns an `entity_id`, which is then resolved
against Postgres. The embedding aids *recall*; the registry provides *truth*.

## 14. Non-negotiable safety rules

Encoded in the system prompt *and* enforced in code:

1. Never state a balance, bet outcome, transaction, or KYC status from RAG — always API.
2. Never emit a URL that did not come from the entity registry.
3. Never state processing times, limits, or fees unless sourced from a verified policy record.
4. Never describe odds, RTP, expected return, or any "strategy" that implies predictable outcomes.
5. Never encourage a user to deposit more, chase losses, or continue playing.
6. Always surface responsible-gaming resources when a user signals distress, chasing losses, or loss of control — this outranks every other intent, including navigation.
7. If a game/page is not in the registry, say it isn't available. Do not improvise.
8. Age-restricted product: never assist an apparent minor.
